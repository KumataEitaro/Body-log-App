## A. UI改善（指摘済み・調査済み）

### A-1. 累計収支「k」単位のローカライズ
- 現状: `changes.tsx` の累計収支カードが `(sumAll/1000).toFixed(1)` + 単位「k」固定
- 問題: 日本では「k」がなじみ薄い。中華圏・韓国も万/만の位取りが自然
- 案: ロケール別の桁表現に切替
  - ja / zh: 「−4.2万kcal」（万で割る）
  - ko: 「−4.2만kcal」
  - en ほか西欧・東南ア: 現行の「−42.3k」を維持（kは自然）
  - 実装は i18n の言語コードで分岐する小さな fmtBigKcal() を lib に置き、
    表・共有ステッカー等で同じ数値を出す箇所があれば全数スイープで統一
- 備考: Intl.NumberFormat の notation:'compact' は Hermes での対応が
  環境依存のため、辞書ベースの手動分岐が安全

### A-2. 概要カード並べ替えの「ぬるぬる」化
- 現状: `components/ReorderableCards.tsx`（自前実装・Jiggleモード）
- ぬるぬるしない原因（実装観点の差分・調査済み）:
  1. Pan ジェスチャーが `runOnJS(true)` で全コールバックJSスレッド実行。
     チャート描画などでJSが忙しいとドラッグ追従そのものが遅延する。
     ベストプラクティスは「追従・退避はUIスレッドのworklet、
     runOnJSは並び確定とハプティクスなど離散イベントのみ」
  2. 退避シフトが setState(shifts) → 全カード再レンダー → useEffect → withSpring
     の経路。スロットが変わるたびReact往復が入り数フレーム遅れる。
     ベストプラクティスは位置をSharedValueのマップに持ち
     useAnimatedReactionで動かす（ドラッグ中の再レンダーをゼロに）
  3. ドロップ確定が setTimeout(230ms)+resetNonce 再レンダーで、
     着地後に一瞬止まる/ちらつく構造
  4. 画面端の自動スクロールが JSの setInterval(16ms)+scrollTo(animated:false)。
     UIスレッドのフレームコールバック＋reanimatedのscrollToに劣る
  5. onLayoutの一回計測なので、チャート遅延ロードで高さが変わると
     スロット判定がずれる
- 対応候補（スパイクで比較）:
  - 案1: react-native-sortables 採用（MatiPl01）。UIスレッド駆動・自動スクロール・
    可変高さ・ハプティクス・Expo/新アーキ対応・活発にメンテ。
    Sortable.Flex を1カラムで使う。props(API)は現行ReorderableCardsを維持し
    内部だけ差し替える
    - 注意: 過去に「外部D&Dライブラリで白画面事故→自前化」の経緯あり。
      採用前に expo-router + NativeTabs 環境での白画面/クラッシュ検証を必ず行う
  - 案2: 自前実装のUIスレッド化リファクタ（上記1〜4の解消）。
    参考: Varun Kukade「drag & drop list 60FPS from scratch (Reanimated+RNGH) Part1〜3」
  - 推奨: 案1のスパイク→問題があれば案2

### A-3. 言語選択リストの並び順をユニバーサル基準に
- 現状: `lib/i18n.ts` の LOCALES が ja, en, zh, ko, es, fr, de, pt, id, th, vi の
  アドホック順（市場優先度っぽい並び）
- 調査結果: 完全な国際規格は無いが、事実上の標準は
  「**ISO 639-1（BCP 47）言語コードのアルファベット順＋表示は各言語の自称（endonym）**」。
  W3C自身のセレクタがこの方式。英語名ソートは文化的バイアス、
  現在のUI言語での照合ソートはスクリプト混在時に破綻するため避ける、が定説
- 案: LOCALESをコード順に並べ替え
  de, en, es, fr, id, ja, ko, pt, th, vi, zh
  （ラベルは現行どおり Deutsch / English / … の自称表記を維持）
  - 任意の親切: 先頭に端末の言語だけピン留め（残りはコード順）
  - 11言語なので探しにくさの実害は小さいが、増えても破綻しない基準になる
- 影響範囲: 設定画面の言語シート。並び替えのみでキー・辞書は不変（低リスク）

### A-4. 王冠ゲーティング導線（MFP式「見えるけど開かない」）
- 元ネタ（2026-08-27動画分析・MFP）: 栄養画面のリストに「炭水化物が最も多く含まれる

  「その他」メニュー最上部にも「👑 Premiumを再アクティブ化」を常設
- 行動科学的な抽象化（調査済み）:
  1. **moment of intent**: 使おうとした瞬間に出す文脈ペイウォールは汎用提示の
     約2倍以上の転換（12% vs 5%）。オンボ直後だけでなく機能タップ時が本命
  2. **curiosity gap**: 機能を隠さず「タイトルと存在」まで見せて中身だけロック。
     知りたい欲が具体化してから壁に当てる
  3. **保有効果**: 「自分の記録データで計算される結果」ほど欲しくなる。
     ロック行の文言は一般論でなく「あなたの28日ぶんから」等の一人称にする
  4. 副次効果: ロック行は有料機能の発見性（存在の告知）も兼ねる
  5. ティザー: 最初の1件だけ見せて残りをロック（法則図鑑の無料3枚と同型）
- BL適用案:
  - 共通 <CrownBadge/>（Lucide Crown・アンバー）＋ gated行タップ→
    /paywall?src=feature_xxx（srcで見出しを文脈化。src=onboardingの既存機構を拡張）
  - 対象候補: 法則図鑑4枚目以降(B-6)／詳細分析（食べ方のクセ・週間ダイジェスト＝
    プレミアム既定義）／AI相談・写真解析の上限到達時（既存429 plan_limit導線と統一）／
    過食予報の詳細／リーンバルク判定の詳細(B-2)
  - **導入タイミング注意**: AI_LIMITS_ENABLED=false（全機能無料）の間に王冠を出すと
    嘘になる。課金有効化と同時にリリースすること
- 参考: RevenueCatのcontextual paywall論、Superwallのfeature gatingガイド

### A-5. ペイウォールの通貨がドル表示（日本語設定なのに$2.99）
- 原因調査済み: コードに$のハードコードは無い。paywall.tsxはStoreKitの
  priceString（地域通貨）をそのまま表示しており設計は正しい。
  ASCの地域価格も設定済み（初期価格.csv: 日本¥9,000等を確認）。
  **サンドボックステスターアカウントの国がUSのため$で返っている**可能性が濃厚
- 対応: ①ASC→ユーザーとアクセス→Sandboxテスターの国=日本のテスターを作成して再確認
  ②実機の設定→App Store→サンドボックスアカウントで確認
  ③本番はユーザーのApple IDの国に自動追従するため、確認だけでコード変更は不要見込み
- 万一fetchOffers失敗時のフォールバック表示を足す場合も、通貨記号は決め打ちしない
