# 設計: よく食べるものをマイ食品に登録するご案内

食事を保存した直後に「オートミールをよく食べるようですね。マイ食品に登録しませんか？」と案内し、
1タップで栄養素まで埋まった登録フォームへ連れていく機能の設計。

**この文書は設計のみ。実装は含まない。**

---

## 0. 前提として埋める穴

着手前に判明した、この機能の土台が欠けている点。

### 穴A: マイ食品の登録UIが存在しない

`settings.tsx` のマイ食品の管理は**一覧と削除だけ**で、追加する画面がない。
テーブルは存在し、デモ用SQLが7件入れているため気づきにくいが、
**現状ユーザーは自分でマイ食品を1件も追加できない**。

これは今回の機能の飛び先であり、同時に単独のバグでもある。最初に作る。

### 穴B: 既存の頻度追跡は流用できない

`lib/foods.ts` の `bl-food-freq-v2` は**マイ食品チップのタップをid基準**で数えるもの。
今回必要なのは**AI解析された食品名を名前基準**で数えるもので、別物。新設する。

### 穴C: 食品名の正規化関数がない

「オートミール80g」と「オートミール1杯」を同一視する処理が存在しない。新設する。

## 1. 全体の流れ

```
食事を保存
   ↓
今日の品目名を正規化して、日単位の出現表に記録
   ↓
判定: 別々の3日以上 / 未登録 / 未辞退 / 今日まだ出していない
   ↓（満たしたら1件だけ）
暗転オーバーレイ + マイ食品チップ列をハイライト
「オートミールをよく食べるようですね。マイ食品に登録しませんか？」
   [あとで]            [登録してみる]
                            ↓
                  登録フォーム（名前・単位・PFC・kcalが埋まった状態）
                            ↓
                        保存 → チップ列に出る
```

## 3. `lib/foodName.ts` — 正規化

### 方針: 誤検知を避け、取りこぼしは許容する

「鶏むね肉」と「鶏もも肉」は栄養が2倍違う。部分一致で寄せると危険。
**正規化後の完全一致のみ**を同一とみなす。

### 落とすもの

```
入力: 「ミックスナッツ（カシューナッツ、アーモンド、クルミ）ひとつかみ（約25g）」
 ↓ 括弧とその中身を除去
     「ミックスナッツひとつかみ」
 ↓ 末尾の分量表現を除去
     「ミックスナッツ」
 ↓ 前後空白・全角半角・大小文字を統一
出力: 「みっくすなっつ」（照合用キー）／表示名は「ミックスナッツ」
```

| 落とす対象 | 例 |
|---|---|
| 数値＋単位 | `80g` `150ml` `2個` `1杯` `1切れ` `1本` `1パック` |
| 数量の副詞 | `ひとつかみ` `ひとつまみ` `少々` `大さじ2` `小さじ1` |
| 括弧の補足 | `（約25g）` `(可食部)` `（ごはん・味噌汁）` |
| 記号・空白 | 全角/半角スペース、`・` 前後の空白 |

### 公開する関数

```ts
/** 照合用キー（小文字・分量なし）。同一判定に使う */
export function foodKey(name: string): string;

/** 表示用の名前（分量を落としただけ。大小文字は保つ） */
export function foodBaseName(name: string): string;

/** 元の名前から分量表現だけを取り出す（登録フォームのunit初期値に使う） */
export function foodPortion(name: string): string | null;
```

`foodPortion('オートミール 1カップ（約80g）')` → `'1カップ（約80g）'`

### 検討したが採用しなかった案

- **表記ゆれの寄せ（カタカナ/ひらがな/漢字）**: 「たまご」「卵」「玉子」を寄せたいが、
  辞書を持つと保守が破綻する。取りこぼしを許容する
- **AIに正規化させる**: 1回の保存ごとにAPI課金が発生する。ローカルで完結させる

## 4. `lib/foodSuggest.ts` — 出現の記録と判定

### 保存する形（AsyncStorage）

```ts
// キー: 'bl-food-seen'
type SeenEntry = {
  name: string;      // 表示用の名前（最後に見た形）
  portion: string;   // 最頻の分量表現
  dates: string[];   // 出現した日付（重複なし・最大14件）
  kcal: number; p: number; f: number; c: number;  // 最頻分量のときの実績値
};
type Seen = Record<string, SeenEntry>;   // キーは foodKey()
```

```ts
// キー: 'bl-food-suggest-declined'   断られた foodKey の配列
// キー: 'bl-food-suggest-shown'      最後に案内を出した日付（1日1件の制御）
```

### 記録

```ts
/** 保存した品目を出現表へ記録する。同じ日の複数回は1回として数える */
export async function recordItems(items: FoodItem[], date: string): Promise<void>;
```

- **同じ日は1カウント**（朝昼晩に3回食べた1日で提案が出るのを防ぐ）
- 14日より古い日付は捨てる（無限に増えない）
- 栄養値は**最頻の分量**のものを保持（分量が揺れても代表値が安定する）

### 判定

```ts
export type Suggestion = {
  key: string; name: string; portion: string;
  days: number;                       // 何日ぶん出たか
  kcal: number; p: number; f: number; c: number;
};

/** 案内を出すべき1件を返す。無ければnull */
export async function pickSuggestion(
  existingNames: string[],   // 既にマイ食品にある名前
  today: string,
): Promise<Suggestion | null>;
```

### 判定条件（すべて満たす）

| 条件 | 理由 |
|---|---|
| 直近7日のうち**別々の3日以上**に出現 | ご指定の「3回」を日単位に。同日の重複で誤検知しない |
| マイ食品に**同名が未登録** | `unique(user_id, name)` があり、登録済みを勧めると失敗する |
| **一度も断られていない** | 同じ提案の再出現は不快 |
| 今日まだ案内を出していない | 1日1件まで。畳み掛けない |
| 栄養値が取れている（kcal>0） | 値が無いと自動入力できない |

複数該当したら**出現日数がいちばん多い1件**。同数なら直近に食べた方。

## 5. `components/SpotlightTip.tsx` — 単発の案内

### 既存GuideTourを流用しない理由

GuideTourは`STEPS`の固定配列を順に進める作りで、タブ間の自動遷移・自動スクロール・
デモ再生まで抱えている。動的な1件を割り込ませると進行状態と干渉する
（ツアー中に提案が出れば二重に暗転する）。

**見た目だけ借りて、進行管理を持たない軽量版を別に作る。**

### ハイライト対象を「チップ列」にする理由

ご指定は「登録の仕方をハイライト」だが、保存直後のユーザーは食事タブにいる。
設定の奥にある管理画面を指しても価値が伝わらない。

**マイ食品のチップ列（ドックの上）をハイライトする。**
「ここに並ぶと1タップで足せます」という**得られる価値**が同じ画面上で見える。

### インターフェース

```tsx
<SpotlightTip
  visible={boolean}
  targetRef={RefObject<View>}   // ハイライトする要素（チップ列）
  title={string}
  text={string}
  primary={{ label: '登録してみる', onPress }}
  secondary={{ label: 'あとで', onPress }}   // 押すと辞退として記憶
  onDismiss={() => void}                     // 背景タップ＝あとで扱い
/>
```

### 描画

- 全画面に半透明の黒（`rgba(0,0,0,0.62)`）
- 対象の実測位置に穴を開け、テーマ色（`C.teal`）の枠で囲む
  → 既存GuideTourと同じ`measureInWindow`による実測方式
- 吹き出しは対象の下（画面下端に近ければ上）に自動配置
- 出現は`Animated`のフェード＋わずかなスケール（既存の作法に合わせる）

### 対象が画面外のとき

チップ列はドックの上にあり常に見えているので、自動スクロールは不要。
ただし**チップが0件のときはチップ列が描かれない**。
その場合は穴を開けず、画面中央のカードとして出す（フォールバック）。

## 6. `components/MyFoodForm.tsx` — 登録フォーム（穴A）

### 入力項目

| 項目 | 初期値 | 必須 |
|---|---|---|
| 名前 | `foodBaseName()` の結果 | ○ |
| 単位 | `foodPortion()` の結果（無ければ`1人前`） | — |
| kcal | 実績の最頻値 | ○ |
| P / F / C | 実績の最頻値 | — |

### 保存時の扱い

- **同名チェック**を先に行い、あれば「すでに登録済みです」と伝えて上書きするか尋ねる
  （`unique(user_id, name)` 違反でエラーを出すより親切）
- 成功したら一覧を再読込し、チップ列に現れることを見せる

### 呼び出し方

2つの入口から同じフォームを使う。

1. **設定 → マイ食品の管理 → ＋ 追加**（空のフォーム）
2. **案内の「登録してみる」**（値が埋まったフォーム）

案内から開く場合、設定タブへ遷移させず**食事タブ上にそのままモーダルで開く**。
保存直後の流れを止めない（設定へ飛ばすと文脈が切れる）。

## 7. `log.tsx` の改修

```
save() が成功した直後:
  1. recordItems(parsed.items, viewDate)
  2. pickSuggestion(既存のマイ食品名, viewDate)
  3. 返ってきたら setSuggestion(s) → SpotlightTip を表示
```

- **保存の成功後のみ**呼ぶ（失敗した内容を学習しない）
- 判定は`await`するが、失敗しても保存の結果表示を妨げない（`try/catch`で握る）
- 「書き換える」で保存した場合も記録する（同じ品目を編集し直しただけなら日付は同じなので二重計上されない）

## 8. 文言（4言語）

| 用途 | 日本語 |
|---|---|
| 見出し | `{name}をよく食べるようですね` |
| 本文 | `直近{days}日で登場しました。マイ食品に登録すると、次からは1タップで足せます。` |
| 主ボタン | `登録してみる` |
| 副ボタン | `あとで` |
| 登録完了 | `マイ食品に追加しました。下のチップから1タップで足せます。` |
| 既登録 | `「{name}」はすでに登録済みです。上書きしますか？` |

`{name}`は正規化後の表示名。プレースホルダの整合は既存の辞書テストが自動検証する。

## 10. 既知の制約（仕様として許容する）

| 制約 | 影響 | 判断 |
|---|---|---|
| 追跡がローカル（AsyncStorage） | 端末を変えるとカウントがリセット | 提案が遅れるだけで害はない。DBに置くと書き込みが増える |
| 表記ゆれを寄せない | 「たまご」「卵」が別扱い | 辞書の保守が破綻するため。取りこぼしを許容 |
| DBの食品名が表示言語に依存 | 英語で使うと`Oatmeal`で記録され、日本語に戻すと別名 | 既存の構造的な問題（運動記録も同様）。この機能で新たに悪化はしない |
| 提案は1日1件 | 複数の候補があっても順番待ち | うるさくしない方を優先 |

## 11. ご指定から変更した3点

| ご指定 | 変更後 | 理由 |
|---|---|---|
| 一週間のうちで3回 | **別々の日で3日** | 朝昼晩に食べた1日だけで提案が出るのを防ぐ |
| 登録の仕方をハイライト | **マイ食品のチップ列をハイライト** | 保存直後の画面上にあり、得られる価値が直接見える |
| （既存ガイド機構を流用） | **同じ見た目の別実装** | ツアーの進行状態と干渉するため |
