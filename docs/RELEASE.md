# リリース/バージョン管理ルール

BodyLoger（native/）のバージョンは **セマンティックバージョニング（SemVer）をコンシューマーアプリ向けに読み替えた基準**で運用する。
形式は `MAJOR.MINOR.PATCH`（例: 1.1.0）。判断に迷ったら下の表で「ユーザーから見て何が変わったか」で決める。

## 上げ幅の定義

### PATCH（1.0.x → 1.0.x+1）— 「直した・整えた」
- バグ修正・クラッシュ修正
- 文言・翻訳・アイコンなど見た目の微調整（できることは変わらない）
- 性能改善・内部リファクタ・依存ライブラリ更新
- 既存機能の小さな磨き込み（アニメーションの調整、余白・フォント等）
- **開発中はビルド用pushのたびに必ず+1**（既存ルール。トレイン衝突事故 90062/90186 の再発防止）

### MINOR（1.0.x → 1.1.0）— 「できることが増えた・変わった」
次のどれか1つでも含む**App Store審査提出**は MINOR を上げ、PATCHを0に戻す:
- ユーザーに見える新機能・新画面・新カード（例: 法則図鑑、きょうの動き）
- ナビゲーション/情報設計の変更（例: 概要のマスタメニュー化、タブ構成変更）
- 新しい許可ダイアログ・権限の追加（HealthKitの読み取り種別追加、通知の新種別など）
- 課金まわりの変化（プラン・価格構成・王冠ゲーティング・上限のON/OFF）
- DBマイグレーションを伴う機能追加
- 判定の目安: **「このバージョンの新機能」欄に書きたいことがあるなら MINOR**

### MAJOR（1.x.x → 2.0.0）— 「別物になった」
- 全面リデザイン、データモデルの刷新、後方互換を切る変更
- ブランド/アプリ名の変更、コンセプトの転換
- （当面は使わない想定。迷ったらMINOR）

## 運用フロー

1. **開発中（main）**: ビルドごとに native/app.json と native/package.json のPATCHを+1。
   ビルド番号はCodemagicの $BUILD_NUMBER が別途自動増加（バージョンとは別物）
2. **審査提出の直前に判定**: 前回のApp Store提出以降の差分にMINOR級が1つでもあれば
   `X.(Y+1).0` に切り上げてから提出。PATCH級のみならそのまま提出
3. **承認されたら**: 承認ビルドのコミットに `vX.Y.Z` 注釈付きタグ＋`release/X.Y.Z` ブランチ。
   main=開発、releaseブランチ=承認版の保全
4. **ホットフィックス**: release ブランチ上でPATCH+1 → 提出 → mainへcherry-pick

## 現状への適用（2026-08-27）

- 承認済み: 1.0.0（App Store）。以降 1.0.16 まで開発パッチが進行中（未提出）
- 1.0.0以降に SSO・課金基盤・実績/ステッカー・オンボv2・概要マスタメニュー化・
  運動タブ再設計など MINOR級が多数入っているため、
  **次のApp Store審査提出は 1.1.0 に切り上げて提出する**
- TestFlight配信は従来どおりパッチ運用のままでよい（1.0.17, 1.0.18, …）。
  提出を決めた時点で 1.1.0 へ切り上げる
