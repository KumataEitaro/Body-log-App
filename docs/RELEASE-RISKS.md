# ストア公開時の不具合リスク棚卸し（2026-08-30）

公開前に潰す/判断すべきポイント。優先度順。✅=コード側は対応済みの強み。

## A. 課金の整合性（最重要・審査と信頼の両リスク）

### A1. ライトプラン「広告なし」だが、広告が未実装 🔴
- 現状: アプリに広告表示は存在しない（文言だけ）。つまり**ライト¥300は無料と差がゼロ**
- リスク: App Store審査4.3（実体のない課金）/購入者の「何も変わらない」→低評価・返金
- 対処の選択肢: ①広告SDKを入れてからライト解放 ②当面ライトを非表示（スタンダード/プレミアムだけで出す） ③初回リリースは課金自体を出さない（現状のRCキー未設定運用のまま）
- **推奨: ③で公開→広告実装とセットで課金列車を分ける**

### A2. AI上限が眠ったまま課金を出すと、スタンダード/プレミアムも実体がない 🔴
- AI_LIMITS_ENABLED=false の間は無料でも無制限＝「AI解析50回/日」を買う理由がない
- **課金解放・王冠表示・AI_LIMITS_ENABLED=true は必ず同時**（3点セット）。バラすと嘘になる

### A3. RC_WEBHOOK_SECRETのローテーション 🔴
- スクショで漏洩済み。課金を有効化する前に必ず再発行（Vercel環境変数とRC側の両方）

### A4. サンドボックスの$表示の確認（既知・TODO4） 🟡
- 国=日本のSandboxテスターで¥になることを確認。本番は自動追従の見込み

## B. App Store審査で突かれやすい点（iOS）

### B1. プライバシーラベル（栄養ラベル）の申告 🟡（熊田さん作業）
- 体重・食事・写真は**サーバー（Supabase/Gemini）に送る＝「収集」扱い**で申告が必要
  （健康とフィットネス／写真／ユーザーID。トラッキングは無し）
- 法則分析は端末内だが、元データがサーバー保存なので「収集なし」とは書けない
- 虚偽申告はリジェクト/削除事由。Data safety（Play側）も同内容で

### B2. 医療アプリ扱いされない文言 🟡
- ✅ AI相談の免責・安全ガード（BMI下限・妊娠フラグ・受診勧奨）は実装済みで強い
- 注意はストアの**説明文側**: 「診断」「治療」「痩せる（効果断定）」を使わない。
  「記録・可視化・一般的な情報」のトーンで書く

### B3. 済んでいる要件 ✅
- Sign in with Apple（Google併設時の必須要件）✅
- アプリ内アカウント完全削除（5.1.1(v)）✅
- 購入の復元ボタン・利用規約/プライバシーポリシーのリンク ✅（**リンク先ページの中身が実在するか要確認**）
- HealthKitの目的文言・読み取りのみ ✅
- iPadは対象外（supportsTablet未設定=iPhoneのみ）→ iPadスクショ不要

### B4. unstable APIへの依存 🟢（運用リスク）
- タブが expo-router/unstable-native-tabs。iOSメジャーアップデートで挙動が変わる可能性。
  秋のiOS新版が出たら早めにTestFlightで確認する習慣を

## C. Google Play固有

### C1. アカウント削除の「Web URL」が無い 🔴（Play必須要件）
- Playのアカウント作成があるアプリは、**アプリ外（Web）からの削除申請URL**を
  ストア掲載情報に載せる義務がある。アプリ内削除だけでは不足
- 対処: bodylog Webに「アカウント削除の手順/申請」ページを1枚作る（小工数・未実装）

## D. グローバル公開の構造的リスク

### D1. 日付境界がJST固定（todayJSTが23ファイル） 🟡→海外本気なら🔴
- 「今日」の判定が全部日本時間。**海外ユーザーは昼の記録が翌日扱いになる**
  （例: 米西海岸は16時間ずれ）。ストリーク・穴埋め・リマインダーの体験が壊れる
- 10言語対応で海外DLは必ず来る。日本先行なら許容だが、
  **海外プロモを打つ前に「端末タイムゾーン化」の大工事が必要**（全保存データの
  日付意味論に関わるため、専用の設計セッション推奨）

### D2. 繁体字・地域別価格は未対応（監査Later群のまま） 🟢
