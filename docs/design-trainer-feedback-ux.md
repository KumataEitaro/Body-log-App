# 設計（UX起点の再検討）: トレーナーさんフィードバック ②〜⑤

前回の設計を「実装しやすさ」ではなく**ユーザーの実際の使用文脈**から書き直したもの。
結論として**前回の推奨を2点撤回**する。

---

## 撤回する2点

| 前回の推奨 | 撤回理由 |
|---|---|
| 運動種目のカスタマイズを、カードと同じ⊖/⊕の編集モードで作る | **設定させる前提が誤り。** 20種目から選ばせるのは、毎日散歩する人にとって「散歩を押すまでの手間が増えた」だけ。編集モードに入る操作も重い |
| デイリーメッセージを「カードの1枚」として作る | **カードは受動的で「開くのが楽しみ」を作れない。** スクロールで通り過ぎるものに期待は生まれない |

---

## ④ 運動種目 — 「設定させない」設計

### 最初に確認したこと: 種目を増やすと今より悪くなる

現状は8種目がグリッドに並び、散歩を記録するのに **運動タブ → 散歩 → 30分 → 記録する** の4タップ。

ここに20種目足すと、**毎日やる散歩が、一生やらない種目に埋もれる**。
一覧が3行を超え、目的のものを探す時間が増える。
「便利にする」つもりの機能が、いちばん頻度の高い操作を悪化させる。

**つまり整理する仕組みは"あったら便利"ではなく、増やすための前提条件。**

### しかしユーザーに設定させるのは誤り

ここが前回の設計の誤り。多くの人は設定画面を開かない。
「まず20種目を整理してください」と要求するのは、8種目固定より悪い。

**アプリが学習すべきで、ユーザーに聞くべきではない。**

### 採用する設計: 頻度で自動的に並ぶ

食事タブのマイ食品チップが**すでにこれを実装している**（`sortByFreq` + 時間減衰スコア）。
同じ仕組みを運動種目に適用する。

- 毎日散歩する人 → 散歩が常に左上。**設定ゼロで最短**
- 週末だけサーフィンする人 → サーフィンが上位に浮く
- 一度も使わない種目 → 自然に沈む

**新しい概念を持ち込まず、既存の資産で解決できる。**

### 表示の形: 食事タブと同じ「▬/▦」切替

食事タブのマイ食品チップは `foodsView: 'row' | 'grid'` を持ち、
▬（1行・横スクロール）と ▦（全展開）を切り替えられる。**同じものを運動にも置く。**

| | 用途 | |
|---|---|---|
| ▬ 1行 | 毎日の記録（頻度上位が見えていれば足りる） | 既定 |
| ▦ 全展開 | 初めての種目を探す（発見） | 必要時 |

**新しい操作を覚える必要がない。** 食事タブで同じことをしているため。

### 隠す操作は「長押し」— 編集モードを作らない

編集モードに入って⊖を押して完了する、は3操作。
**チップを長押し → 「この種目を隠す」** で1操作。

長押しは既にアプリ内の慣習になっている（記録行の長押し、マイ食品チップの長押しドラッグ）。
隠した種目は ▦ 全展開の末尾に「隠した種目」として並べ、タップで戻せる。

**専用の設定画面を作らない。** 設定項目を増やすことは、それ自体がUXの劣化。

### 「アイコンのサイズ」について

トレーナーさんは「アイコンのサイズもカスタマイズできると便利」とおっしゃったが、
**サイズ設定は追加しない**方がよいと判断した。設定項目が増えるほど、初回の負担が増える。

代わりに **チップ自体を今より大きくする**。現状のチップは絵文字17px・文字11pxで小さい。
①の指摘（文字が小さくて情報の優先順位がわからない）と同じ問題が運動タブにもある。
▬/▦ の切替で密度は2段階選べるので、これで実質的な要望は満たせる。

### 追加する種目（Compendium of Physical Activities 2011 準拠）

トレーナーさんが挙げたサーフィンを含め、日本のユーザーが実際にやるものを中心に。

| 種目 | METs | 種目 | METs |
|---|---|---|---|
| 🏄 サーフィン | 3.0 | 🎿 スキー・スノボ | 5.3 |
| 🥾 登山・ハイキング | 6.0 | 💃 ダンス | 5.0 |
| ⛳ ゴルフ（歩き） | 4.3 | 🎾 テニス | 7.3 |
| 🏸 バドミントン | 5.5 | 🏓 卓球 | 4.0 |
| 🏀 バスケットボール | 6.5 | ⚾ 野球 | 5.0 |
| 🥊 格闘技・武道 | 10.3 | 🧗 ボルダリング | 7.0 |
| 🪢 縄跳び | 11.8 | 🚲 エアロバイク | 6.8 |
| 🪜 階段のぼり | 8.8 | 🛒 買い物・外出 | 2.3 |
| 👶 子どもと遊ぶ | 3.5 | 🌱 庭仕事 | 3.8 |

**注意**: METsは代表値であり、強度によって実際は上下する。
アプリ内に出典を明記し、「目安」であることを添える（既存の「約○kcal消費」表記と整合）。

## ④の前提: 直さないと壊れ続ける2点

### バグA: 種目名が翻訳された状態でDBに保存されている

```
text: `🏃 ${a.n} ${actMin}分（約${kcal}kcal消費）`   // a.n = t('散歩') の結果
```

英語で使うと `🏃 Walk 30分（約101kcal消費）` と混在し、言語を戻すと別の種目として扱われる。

**ユーザーに見える症状は「言語を切り替えたら分析がおかしくなった」**で、原因が見えない。

**修正方針**: `activities()` に `canon`（日本語固定）を持たせ、
**DBには canon、画面には翻訳名**。既存の `ex`（'オフ'/'軽い'）が日本語固定で保存されている
慣習と一致する。スキーマ変更もマイグレーションも不要。

既存の混在データは、ベータ2名の段階なので**そのまま許容し、以後を正す**。

### バグB: 種目の選択がindex依存

```
const [actIdx, setActIdx] = useState<number | null>(null);
const a = activities()[actIdx];
```

**並び順が変わると選択が別の種目にすり替わる。**
頻度で並べ替える設計にすると、この瞬間にバグ化する。

**修正方針**: 種目に安定した `id`（`'walk'` `'surf'` …）を持たせ、`actId` で選択する。
頻度スコアのキーにも、DBのcanon名の導出にも同じidを使う。

**この2つはどちらも、④の実装前に必ず直す必要がある。**

## ②③⑤ デイリーメッセージ — 「期待」をどう作るか

### カードでは期待が生まれない

前回は「カードの1枚として並べ替え可能に」と設計した。撤回する。

**カードはスクロールで通り過ぎるもの。** 「開くのが楽しみ」の反対にある。
そして並べ替えできることは、この機能にとって価値ではない。

### 何が期待を作るのか

3つ揃う必要がある。

1. **毎回違う**（同じものが出たら二度目から見ない）
2. **開いてすぐ目に入る**（探させたら期待にならない）
3. **開いた行為が報われる**（読む価値がある内容）

### 配置: ヘッダーとヒーローの間の「1行の帯」

| 案 | 判断 |
|---|---|
| ヒーローより上に大きく置く | ✕ ①の指摘（情報の優先順位が不明）が再発する |
| カードの1枚 | ✕ 受動的で期待が生まれない |
| 起動時に全画面で出す | ✕ 「早く記録したい」を妨げる。毎日は邪魔 |
| **ヘッダー直下の1行の帯（約40px）** | **○** |

**1行の帯**なら:
- ヒーローをほとんど押し下げない → ①の情報階層を守る
- 開いた瞬間に目に入る → ③⑤の「上に出る」を満たす
- タップで展開して全文が読める → 邪魔にならず、深く読める
- その日は閉じられる／設定でオフ → トレイナーさんの「オプションで」

そして**動き**は、帯が開いた時に一度だけ滑り込み、キャラがゆっくり呼吸する程度。
⑤で評価された「動きがあってよい」を、広告なしで満たす。

### 内容の優先順位: 自分のデータが最優先

**あすけんの模倣にしない。** あすけんの未来ちゃんは点数と一般的コメント。
BodyLogが持っているのは**その人のデータから出た事実**で、これは他社が真似できない。

| 優先 | 種類 | 例 | 元データ |
|---|---|---|---|
| 1 | 個人の傾向 | 「金曜は食べすぎが2.8倍。今日は金曜です」 | `bingeAnalysis` |
| 1 | 食材の反応 | 「生姜焼き定食の翌日は平均−146g」 | `insights` |
| 1 | 継続 | 「7日連続で記録できています」 | `entries` |
| 1 | 停滞の説明 | 「3週間横ばい。水分で隠れやすい時期です」 | `adaptive` |
| 2 | コラム抜粋 | 「同じカロリーでも太り方が違う理由（3分）」 | `columns` |
| 3 | 一般の豆知識 | ネタ切れ防止の予備 | 事前執筆 |

**すべてローカル計算。API課金はゼロ。**

トレーナーさんが例示した「山の日はなぜ山の日か」のような無関係な豆知識は**優先度3に置く**。
無関係な情報はアプリの焦点を薄めるため、自分のデータが出せる限りそちらを出す。

### 絶対にやらないこと: 点数

あすけんは100点満点で採点する。**BodyLogでは採点しない。**

過食分析であれだけ慎重に「責めるためではない」と書いているのに、
キャラが「今日は45点」と言えば台無しになる。
**観察と次の一手を渡し、その人の一日を評価しない。**

### キャラクター: 絵描きがいない制約への答え

下手なイラストは無いほうがマシ。3案を検討した。

| 案 | 判断 |
|---|---|
| 絵文字を使う | ✕ 意味と見た目が噛み合わず、安っぽく見える |
| 既存のAIコーチのロゴを流用 | △ ロゴであってキャラではない。表情を持てない |
| **円と角丸だけの幾何キャラをSVGで描く** | **○** |

- テーマカラー（12色）を継承する → **テーマを変えるとキャラの色も変わる＝それ自体が動的**
- 表情は4つだけ（通常・喜び・気づき・応援）。メッセージの種類で選ぶ
- 線が少ないので、どのサイズでも崩れない

将来イラストを用意できたら差し替えられるよう、**表示部分を1コンポーネントに閉じる**。

## ⑤ 広告 — 見送りの判断は変えない

| 理由 | |
|---|---|
| 審査 | 広告SDKはトラッキング申告を変える。いま「トラッキングなし」で申請する前提が崩れ、ATTダイアログの実装が必要になる場合がある |
| 信頼性 | 減量アプリがサプリ広告を出すと信頼を損なう。**トレーナーに見せて評価してもらう用途と矛盾する** |
| 時期 | v1.0の目的は「公開して使ってもらう」。収益化は早い |

トレーナーさんが評価したのは「**動きがあって**よい」の部分。
それは上記のメッセージ帯で満たせる。

## 実装順序（UXの効果が大きい順）

| 順 | 内容 | UXへの効果 |
|---|---|---|
| 1 | バグA・B（canon保存＋id選択） | 見えないところでデータが壊れるのを止める。②の前提 |
| 2 | 頻度ソート＋▬/▦切替＋チップ拡大 | **種目を増やす前に、既存8種目でも探しやすくなる** |
| 3 | 種目18件の追加＋長押しで隠す | ここで初めて「増やしても悪化しない」状態になる |
| 4 | デイリーメッセージ帯（データ由来のみ） | 開く動機を作る |
| 5 | キャラクターと表情 | 4の見た目を仕上げる |

**2を3より先にやるのが重要。** 逆順にすると、一時的に「探しにくい20種目」の状態を作ってしまう。

そして4は**データ由来のメッセージだけで先に出す**。キャラなしでも成立する内容を用意してから、
5で見た目を足す。逆にすると「キャラはいるが言うことがない」状態になる。
