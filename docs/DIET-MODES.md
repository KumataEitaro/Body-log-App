# 食事制約モード（除外アラート）設計案 — 2026-09-02

**未実装・設計のみ。** ビーガン/グルテンフリー等の「食べない物」を登録すると、
写真解析・メニュー解析の結果に対して該当の可能性を警告する機能。

熊田さんの指摘どおり **モードを個別実装しない**。「除外リスト＋自由記述の排除プロンプト」
という1つの器にして、ビーガンもグルテンフリーもハラールも低FODMAPも同じ仕組みで動かす。

---

## 1. データモデル（1つの器）

```
profiles.diet_modes  jsonb   -- 有効なプリセットのキー配列 ['vegan','gluten_free']
profiles.diet_custom text    -- 自由記述の排除指定（例:「えび・かに。パクチーも無理」）
```
※ 既存の `constraints_note`（AI相談用の恒常的な前提）とは**別カラム**にする。
あちらは「提案してほしくない」ための好み、こちらは**アラートの判定基準**で、
誤検知のコストが桁違いに違うため混ぜない。

### プリセット（コード同梱・辞書は端末内）
| key | 名前 | 判定に使う語のイメージ |
|---|---|---|
| vegan | ビーガン | 肉/魚/卵/乳/はちみつ/ゼラチン/かつおだし/ラード… |
| vegetarian | ベジタリアン | 肉/魚/ゼラチン/だし系 |
| gluten_free | グルテンフリー | 小麦/大麦/ライ麦/パン粉/麩/しょうゆ（※注記）/天ぷら衣… |
| halal | ハラール | 豚/アルコール/みりん/ゼラチン… |
| dairy_free | 乳製品なし | 牛乳/バター/チーズ/生クリーム/ホエイ… |
| （自由記述） | 自分で決める | ユーザーの言葉をそのままAIへ渡す |

- 辞書は `native/src/content/dietRules.ts` に**日本語の生値**で持つ（i18nは表示名だけ）。
- 「しょうゆ＝小麦を含むことが多い」のような**グレー語**は別枠にして、
  黒（含む可能性が高い）と灰（製品による）で警告の強さを変える。

## 2. 判定の二段構え（重要）

1. **端末内の語マッチ**（無料でも動く・オフラインでも動く）
   AI解析が返した品目名・原材料テキストに対して辞書マッチ。速い・無料・説明可能。
2. **AIへの排除プロンプト**（プレミアム）
   解析リクエストに「このユーザーは次を避けています: {list}{custom}。
   結果の各品目について、該当の可能性を high/maybe/none で必ず返すこと」を注入。
   写真だけで判断できない場合は必ず maybe を返させる（**断定させない**のが要）。
   → `lib/parseFoodPrompt.ts` / `lib/menuAdvicePrompt.ts` の両方に注入口を作る。

**なぜ二段か**: ①だけだと未知の表記に弱く、②だけだとオフライン・上限到達時に無警告になる。
「無料でも最低限は守られる」ことが、この機能を安全に配る前提。

## 3. どう ON にするか / どこで設定するか

- **設定 → 新セクション「食事の制約」**（アカウント設定の下・新規行）
  - プリセットのトグル一覧（複数選択可）
  - 「その他（自由記述）」の複数行入力
  - **最上部に必ず免責パネル**（§6）を置き、初回ONのときだけ**同意チェック**を必須にする
    （「理解しました」を押さないとONにできない。AsyncStorage＋profilesに同意日時を保存）
- オンボーディングには**入れない**（初回の負荷を増やすし、同意を流し読みさせたくない）
- 相談タブの「前提を設定」導線とは並列に置き、相互リンクだけ張る

## 4. プレミアム限定にする場合の導線（無料にも存在を知らせる）

推奨: **「端末内の語マッチ（黒判定のみ）＝無料 / AI判定・自由記述・メニュー解析＝プレミアム」**

理由: アレルギー・宗教は安全と尊厳に関わるので、**完全に有料の壁の裏に置くのは危うい**
（審査でも「健康被害の可能性がある機能を課金の裏に隠した」と見られると分が悪い）。
最低限の保護は無料に置き、精度と網羅性で有料に差をつける。

- 設定画面ではプリセット行の右に 👑 を出し、無料でも**存在と内容を読める**
  （王冠ゲーティングの curiosity gap 方針どおり）
- 無料でONにすると「かんたん判定（辞書のみ）で動いています。AIによる読み取りと
  メニューの判定はスタンダード以上です」の1行＋👑
- 課金導線は `/paywall?src=diet` （SRC_COPY追加: 「食べないものを、AIが見張る」）

## 5. 検知したときのアラートUI

**強さは3段階。断定しない・食べる自由を奪わない。**

| 判定 | 見せ方 | 文言の型 |
|---|---|---|
| high（黒） | トレイの該当品目チップに赤い縁＋⚠️、トレイ上部に警告行 | 「**{品目}** に{制約}の対象が含まれている可能性が高いです」 |
| maybe（灰） | 品目チップにアンバーの点、警告行はアンバー | 「{品目}は製品によって{制約}の対象を含みます。表示をご確認ください」 |
| none | 何も出さない（無警告＝安全の保証ではない旨は§6で常設） | — |

- **保存はブロックしない**（食べたものを記録する自由は絶対に奪わない）。警告は情報提供のみ
- メニューおすすめ（B-11）では、該当する候補を**推薦から外す**のではなく
  「⚠️ 対象の可能性」を添えて順位を下げる（消すと「安全な物だけ出た」と誤解させる）
- 触覚は使わない（不安を煽らない）。音も出さない
- 警告行に必ず「これは推定です」の一言と、詳細（§6）へのリンクを添える

## 6. 免責（米国訴訟リスク対策・ここが最重要）

前提: 食物アレルギーは**死亡し得る**。AI画像判定に安全を委ねさせた瞬間に、
このアプリは製造物責任の議論に足を踏み入れる。設計で「委ねさせない」ことが唯一の防御。

### 実装する防御（多層）
1. **機能名から「アレルギー」を外す** — 「食事の制約」「食べないもの」と呼ぶ。
   `allergy` / `allergen` / `safe` / `free of` という語をUIに使わない
   （"gluten-free" と断定する表示は、FDAの表示規制の文脈と衝突しうる）
2. **同意ゲート（初回ON時）**: 全文表示＋チェックボックス＋同意日時をDBに記録
   - 「この機能は**推定**であり、**アレルギーや医学的な食事制限のための安全確認には使えません**」
   - 「**必ず製品の原材料表示と、店舗・製造者への確認を優先してください**」
   - 「警告が出ないことは、対象が含まれないことを意味しません（見落とします）」
   - 「重篤なアレルギーがある方は、この機能に依存しないでください」
3. **警告行にも毎回1行の免責**（同意は薄れるので、現場に置く）
4. **無警告時の常設表記**: 解析結果の下に薄く
   「表示のない品目も、対象を含む可能性があります」を常時出す（沈黙を保証と誤読させない）
5. **利用規約・プライバシーポリシーの改訂**（/terms）に本機能の条項を追加。
   準拠法・責任限定は既存条項に従うが、**この機能の非保証を明示的に列挙**する
6. **App Store / Play の説明文**でも「推定であり安全確認用ではない」と明記
7. **ログ**: 同意日時・バージョンを残す（後日の紛争で「何に同意したか」を再現できるように）

### やらないこと（訴訟リスクを増やす）
- 「安全です」「食べられます」の**肯定的断定を絶対に出さない**（否定的警告のみ）
- 緑のチェックマーク・「OK」バッジ等の**安全そうに見える視覚表現を使わない**
- 医療・栄養指導の文脈に踏み込まない（既存の安全ガードと同じ線）

参考にした実務: 同種アプリ（Allergy Scanner / SnackPro 等）はいずれも
「contains / may contain / doesn't appear to contain」の**三値**で、
"doesn't appear"（＝断定しない）表現と医療免責を併記している。
AI由来のアレルギー判定は責任分界が未成熟という指摘もあり、
**開発者側は「安全確認の代替ではない」と明示する以外に守りがない**。
